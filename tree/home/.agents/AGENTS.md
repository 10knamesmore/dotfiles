## 沟通

- 不确定的事不要编造。源码事实通过当前代码查证并提供 path/to/file:line；外部事实引用文档或其他可核验来源；设计判断说明理由，区分事实、推断与建议。
- 非平凡改动前先说明方案。用户已明确要求实现，且当前对话已确定目标、范围和关键行为时，视为方案已对齐，直接推进，不重复确认。尚有会改变产品行为、范围或权限的未决选择时，提出具体方案并等待决定；期间继续不依赖该决定的工作。其他明确批准要求仍然适用。
- 任何时候提到代码原文, 使用 path/to/file:line + md 代码块snippet, 不要说一大堆名词
- 方案对比先给推荐项和理由；用户提供源码路径和行号时重新读取。中文不常见的技术术语保留英文。

## 工作方式

- 每次改动都做与风险相称的验证，但不默认新增测试。优先使用编译器、已有测试和真实运行。新增测试应保护明确的业务契约或具体回归，且提供已有验证缺少的价值；不复制实现、不固定无业务意义的内部细节、不为测试引入额外架构或假设性防御。符合这些条件的测试无需单独请求授权。不得为使实现通过而削弱断言，或擅自改变测试表达的业务契约；不把测试数量、覆盖率或新增验证设施当作工作完成度。
- 不新增没有当前需求、既有契约或实际失败证据支持的兜底、兼容层与防御机制。实现当前需求必需的错误处理直接完成；会改变产品行为、范围或权限的选择先讨论。
- 当用户对话中途插入其他信息时， 默认接受而不是转换目标，大多数情况下用户需要的是多目标并行
- 声明"完成 / 修好 / 通过"前先实际验证（跑命令看输出）；没验证的步骤如实说，失败不粉饰
- 选择实现方案时先检查项目已有依赖，优先复用成熟、有人维护的能力，没有明确理由别自己写轮子。方案不明确或需要比较实现路线时，再参考成熟产品与开源实现。
- 按共同职责和生命周期组织模块、类型与函数。属于同一概念的字段用子结构体组织，相关文件放进同一模块目录；不为嵌套而嵌套，职责拆分应让维护者更容易理解。
- 任何业务关键路径, **打好日志埋点**
- 变量命名, 注释， prose, 类型/api/函数/模块设计 都必须以`human facing`为第一原则， 没有达到`作为0先验知识的人类维护者能一眼看出来大致意思`就是不合格
- 未经当前任务授权，不 commit 或 push。修改匹配周围代码风格；用户界面的展示文案由前端根据结构化状态生成，不直接展示后端内部错误文本。
- 注释说明领域知识、不变量和误用后果；持久文档与注释遵循 prose-standard，不复制会话中的方案讨论。

## 工具偏好

- 文本搜索用 `rg`，文件查找用 `fd`。`rg -n` 显示行号，`-r` 是替换而非递归；字面量用 `-F`，查隐藏或被忽略的文件时显式选择 `rg -uu` 或 `fd -u`。
- 结构化代码搜索可用 `ast-grep`；重写先预览 diff，再显式应用。
- Python 使用 `uv run python`，依赖用 `uv add`，临时工具用 `uvx`；JS 包管理使用 `pnpm`。Rust 测试优先已有 `cargo nextest` 入口，配合项目要求的 fmt/clippy。
- GitHub 操作用 `gh`；深入研究源码时使用上面约定的 `~/Documents/repos`。
- 共享 PreToolUse hook 会按 `~/.agents/hooks/pretool.toml` 启发式拦截工具误用与高风险操作；它不替代宿主的 sandbox 和权限。
- 修改 Rust 或 Python 时，分别读取 `~/.agents/rules/rust.md` 或 `~/.agents/rules/python.md`；项目的具体约定优先。
