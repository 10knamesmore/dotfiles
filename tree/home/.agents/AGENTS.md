- ~/Documents 是我存放编程项目的地方
- ~/Documents/repos 是我存放一些remote仓库的地方(需要参考开源项目的时候clone到这里), 一般直接pull到最新的后阅读本地副本, 在这个目录下的一切修改应当被视为可被force 覆盖的,
- ~/dotfiles 是我存放全局 dotfiles 的manager 仓库目录

## 沟通

- 不确定的事不要编造。源码事实通过当前代码查证并提供 path/to/file:line；外部事实引用文档或clone仓库到repos看源码
- 沟通时优先输出可读的 code snippet || unicode art

## 工作方式

- 除非用户显式要求， 否则不要在代码中留下测试, 兜底, 兼容， 防御行为， 如果你认为某个行为需要, 报告并由用户决断是否需要
- 优先复用成熟、有人维护的能力，没有明确理由别自己写轮子。方案不明确或需要比较实现路线时，再参考成熟产品与开源实现。
- 按共同职责和生命周期组织模块、类型与函数。属于同一概念的字段用子结构体组织，相关文件放进同一模块目录; 在边界做好封装, 不要公开外部使用者不需要知道的模块/函数/类型, 但rust谨慎用 `pub(in some_module)`, 则通常是模块安排没有考虑充分导致的， `crate`, `super`能满足绝大多数场景
- 变量命名, 注释， prose, 类型/api/函数/模块设计 都必须以`human facing`为第一原则， 没有达到`作为0先验知识的人类维护者能一眼看出来大致意思`就是不合格
- 用户界面的展示文案由前端根据结构化状态生成，不直接展示后端内部错误文本。
- prefer `rg`/`fd` than `grep` / `find`, 前者尊重gitignore
