# 评估与迭代

仅在需要比较效果或排查触发问题时使用。根据项目约定选择实际运行、用户评阅或成组比较，不要求固定脚本、JSON schema、浏览器 viewer 或 agent 平台。

## 选择请求与判断标准

从两三个真实风格的请求开始，覆盖主要用途和容易失败的边界。明确输入材料、期待产物和成功条件；需要由用户判断的领域标准，先与用户对齐。

客观检查关注真实结果，例如转换后的数据是否保留、计算是否正确、生成的程序是否能运行，而不只是文件存在或回答提到某个词。能由已有解析器、编译器或工具验证的就使用它们。风格、可读性和设计质量保留人工判断，说明判断依据，不伪装成精确测量。

比较前确定标准，不为了让某个结果通过再修改标准。发现标准本身有误时可以修正，但应对所有比较版本重新应用。

## 公平比较

- **新建 skill：** 对比使用 skill 和不使用 skill。
- **修改已有 skill：** 修改前保留旧版本及配套资源，用旧版作为基线；后续比较注明采用初始版还是上一版。

两组使用相同请求、输入、模型、工具权限和执行预算。尽量只改变 skill，使用独立的新上下文；基线不应意外读取正在评估的 skill，也不应继承其起草过程、修订理由或参考答案。若宿主自动加载 skill，先确认能隔离加载；无法隔离就说明限制，不宣称这是无 skill 基线。

有隔离执行能力时按宿主提供的方式运行，独立任务可以并行，但每个任务使用不同的工作目录，不共享可变产物。没有这种能力时做顺序试用并说明上下文可能影响结果，不将自评描述成独立比较。

委派任务时提供：

```text
任务：原始用户请求
输入：材料或文件路径
使用的 skill：当前版路径、旧版路径，或明确不使用
输出：需要交付的产物，以及本次独立的保存位置
约束：允许的工具、操作范围和完成条件
```

评估不能扩大原请求的操作授权。涉及发布、外部写入或真实数据修改时，使用经过授权的隔离环境；否则只验证可安全执行的部分，并说明哪些行为未验证。

需要保存记录时放在安装目录外的临时或已忽略目录，按轮次、请求和版本区分。保存请求、版本、输入来源、产物、可获得的执行记录和评价证据，避免下一轮覆盖上一轮。耗时、token 和工具调用量只记录宿主实际提供的值；缺失就标明不可得，不从输出长度估算 token。

## 评价产物与执行过程

逐项给出满足、未满足或无法核实，并指向具体产物或执行证据。没有证据不能计为成功；同时区分结果失败与证据不足。不因文件名正确、格式看似完整或执行者声称完成就判定成功。

检查预设标准之外的重要问题：产物是否实用，是否丢失输入信息，是否有未验证的事实或过程声明。也检查标准本身：明显错误的输出是否仍会通过，关键要求是否无人检查。

同时阅读执行过程，确认哪些步骤帮助了结果、哪些造成无效工作；无法获得执行记录时，不推断内部原因。不要把工具不可用造成的失败直接归因于措辞问题。

展示每个请求对应的产物和主要差异，再汇总结果。关注总体数字会掩盖的情况：

- 两组都通过的检查可能无法说明 skill 的增益，但仍可保护基本要求。
- 两组都失败可能是任务、环境或检查标准的问题。
- 使用 skill 后反而失败的请求应优先调查。
- 重复运行结果不稳定时，报告波动，不凭单次结果下结论。
- 质量提升是否伴随明显的时间或资源成本，是否值得由实际用途决定。

只有重复运行且数据充分时，才汇总均值、离散程度和版本差异；单次运行只报告观察值，不声称统计上的提升。用户需要看产物时直接提供文件或当前环境支持的预览，不强制新建 viewer。

需要降低版本偏见时，可让独立评阅者只看任务、标准和匿名标为 A/B 的产物，不提供版本身份。先评价实际任务完成情况，允许相当或都不合格；评价结束后再结合版本和执行记录分析原因。

## 改进 description 的触发范围

把触发效果与执行效果分开：会正确执行不等于会在正确时机读取 skill。

准备两类请求，并使用用户会实际输入的措辞、上下文和细节：

- **应该触发：** 同一意图的不同表达，包括不提 skill 名称但确实需要其能力的请求。
- **不应该触发：** 共享关键词但目标不同的相邻任务，而不只是明显无关的请求。

在目标宿主中观察是否实际选择或读取了 skill；不要显式要求使用它，否则验证的是指令遵循而不是自然触发。没有可观察的调用记录时，只能检查描述与请求是否匹配，不能声称测得触发率。

根据漏触发和误触发调整任务范围、典型意图和排除项，不堆积样本中的词语。保留一批未用于修改的新请求检查效果，不反复用同一批请求挑选描述并称为独立验证。展示修改前后的描述和实际观察到的变化；批量重复运行前与用户确认范围和成本。
