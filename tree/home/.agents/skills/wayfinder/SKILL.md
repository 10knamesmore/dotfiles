# Wayfinder

先明确要达成什么，再通过代码和实际结果探索实现。Brief 保存人需要一眼看懂的目标与边界，不是开工前必须完成的设计规格。

## 从当前需要开始

- **想法还不清楚：** 先利用已有对话、项目约定和相关源码查证事实，再澄清会改变目标、行为、范围或代价的问题。按眼前问题调查，不先扫描整个问题空间。
- **共识已经形成：** 直接整理，不重新访谈，也不把暂拟方案写成已确认要求。
- **继续已有任务：** 读取任务说明，结合当前代码与实际验证确认进展，选择下一步；不只凭旧摘要认定工作已完成。

## 澄清与推进

- 一次只问一个会改变当前选择的问题。把确实需要用户决定的行为、范围和取舍留给用户；可逆的内部实现选择由 agent 在编码和验证中决定，不逐项请求批准。
- 用户难以凭抽象文字判断时，用具体输入输出、接口草图、小 diff 或最小运行结果帮助讨论，不用更多文字替代证据。只有需要验证假设时才做原型，不把原型设为必经步骤。
- 尚未确认、且影响用户可见行为或难以逆转的选择（如权限与持久化数据规则），应在相关实施前澄清；已有明确要求直接遵循。其他未知量可以在实现中逐步消除，不要求先定完整方案。
- 用户只要求讨论或整理时，不自行实施。已授权实现时，围绕可观察结果边读代码、边实现、边验证，按项目约定做与风险相称的检查。发现假设错误就调整实现；只有涉及目标、边界或用户取舍时才重新确认。
- 在授权范围内继续推进，直到完成、用户暂停或遇到实际阻塞。只暂停依赖阻塞事项的工作；不把一次讨论、一个切片或一份文档当成交付上限。commit 或 push 只按用户或项目的明确授权执行。

## 简短任务说明

只有用户要求落盘或确实需要跨会话续做时才保存 Brief；一次会话可完成的明确任务直接做。每个目标一份文件，不建子任务文档、依赖图或状态机。

位置遵守项目约定；没有约定时用 `briefs/<task-slug>.md`。已有任务说明直接更新，不另建副本。Brief 是本地工作文件，写入前确认 Git 已忽略；未忽略时加入仓库本地 exclude，不提交入库。

用几段文字或少量列表，让人一眼看出目标、边界和下一步。没有固定模板，也不为填齐栏目扩写。按需保留：

- **目标与完成条件：** 为什么做，完成后有什么可观察的变化。
- **边界：** 已确认的约束、取舍和明确不做的内容。
- **帮助理解的例子：** 暂拟 API、关键数据形状、典型调用或输入输出。标明哪些只是草图，哪些是用户要求固定的约束；不展开完整接口清单、内部调用关系或逐文件实施步骤。
- **续做现场：** 几行已完成、未完成、实际验证结果、当前阻塞与下一步；必要时链接源码入口。不抄录调查过程、命令输出或访谈记录。

确认目标或边界改变时，修改对应内容；内部实现变化不要求同步草图。暂停、恢复或完成工作时，把现场信息替换成当前事实，不追加流水账。过时草图在整理时删除，或换成源码入口，不维护第二份接口定义。只有实际结果满足完成条件，才能记录完成；未验证和未完成项必须明确。

## 长期文档

确实需要长期保留、又无法从代码看出的业务含义或设计原因，写在就近注释或已有文档中，不默认新建文档。持久文字遵循 [prose-standard](../prose-standard/SKILL.md)。
